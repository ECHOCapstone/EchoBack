# 023. Recording Service — upload (3-mode + TransactionSynchronization)

## Goal
3-mode 녹음 업로드 흐름을 구현한다. IMPLEMENTATION_PLAN §6 Phase 4 의 단계 순서를 엄격히 따른다: parent resolution → mode detect → cross-parent invariant → /g2p (canonical 산출) → /analyze (canonical 포함 호출) → LLM guidance → storage save → **TransactionSynchronization 등록(즉시, entity persist 앞)** → entity 정적 팩터리 + repository.save. storage save 이후의 모든 실패에서 `afterCompletion(status)` 콜백이 `status != STATUS_COMMITTED` 일 때 `recordingStorage.delete(audioPath)` 로 정리.

서비스 도메인 불변식 #1, #11, #12, #15 (그리고 #2 검증 재활용) 본 task 책임.

## Acceptance Criteria
- [ ] `RecordingService.upload(userId, request, audio): RecordingUploadResponse` (`@Transactional`):
  - parent resolution: `scriptId` / `stepId` / `sessionId` / `sessionSentenceId` 조합으로 3-mode 결정.
  - cross-parent 사전 검증 (서비스 #2 의 컨트롤러 진입 경로 검증).
  - 1) `g2p(targetText)` → canonical 산출.
  - 2) `analyze(audioBytes, canonical)` → AnalyzeResult.
  - 3) `llmClient.summarizeRecording(...)` → RecordingGuidance.
  - 4) `recordingStorage.save(userId, wavBytes)` → audioPath.
  - 5) **즉시** `TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() { afterCompletion(status){ if(status!=STATUS_COMMITTED) storage.delete(audioPath); } })`.
  - 6) `Recording.forXxx(...)` 정적 팩터리 + `recordingRepository.save(recording)`.
- [ ] AUDIO_DECODE_FAILED: 빈 / 형식 오류 audio 입력 시 (예: 헤더 검사 실패) `BusinessException(AUDIO_DECODE_FAILED)`.

- [ ] 서비스 도메인 불변식 테스트:
